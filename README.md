# Smart Campaigns — Email Marketing Agent Panel

بازسازی دقیق UI داشبورد دارک/گلس‌مورفیسم (نسخه‌ی مرجع: «Lucky Swaps») با محتوای
**پنل مدیریت و اجرای ایجنت ایمیل مارکتینگ**. بدون هیچ کتابخانه‌ی UI — فقط React + CSS خام.

## اجرا

```bash
npm install
npm run dev
```

مرورگر خودش روی <http://127.0.0.1:4300> باز می‌شود.

> **چرا 4300 و چرا `127.0.0.1`؟**
> ۱) با هاست پیش‌فرض («localhost») ویت فقط روی `::1` گوش می‌داد و `127.0.0.1` کانکشن
> refused می‌گرفت. الان `server.host = '127.0.0.1'` است.
> ۲) پورت‌های ۵۱۷۳ تا ۵۱۷۵ روی این سیستم توسط dev serverهای دیگر اشغال بودند، برای همین
> پورت اختصاصی ۴۳۰۰ با `strictPort` ست شده تا آدرس همیشه ثابت باشد (اگر اشغال بود،
> به‌جای پریدن روی پورت تصادفی، صریحاً ارور می‌دهد).

بیلد پروداکشن:

```bash
npm run build
npm run preview
```

## سطح‌ها: بوردر گرادینتی + Squircle

هر دو نیتیو هستند و هیچ لایبرری‌ای لازم نیست (`src/styles/surface.css`):

**۱. بوردر ماسک‌شده با گرادینت** — به‌جای `border: 1px solid`، یک حلقه‌ی ۱ پیکسلی از
اختلاف ماسک border-box و content-box ساخته می‌شود:

```css
.card::after {
  content: ""; position: absolute; inset: 0;
  padding: 1px; border-radius: inherit; corner-shape: inherit;
  background: var(--ring);            /* linear-gradient(145deg, …) */
  mask: linear-gradient(#000 0 0) content-box, linear-gradient(#000 0 0);
  mask-composite: exclude;
}
```

سه طعم رینگ داریم: `--ring` (کارت‌ها)، `--ring-soft` (کنترل‌های کوچک)، `--ring-blue`
(سطح‌های آبی مثل Challenge و CTA).

**۲. Squircle نیتیو** — `corner-shape` در Chrome 139+ ساپورت می‌شود:

```css
@supports (corner-shape: squircle) {
  .card, .chip, .cta, … { corner-shape: squircle; }
  .account, .info-toggle { corner-shape: superellipse(2.2); }  /* پیل‌ها */
}
```

مرورگرهای بدون ساپورت (فعلاً Firefox/Safari) همان گوشه‌ی گرد معمولی را می‌گیرند —
هیچ چیزی نمی‌شکند. شعاع‌ها داخل بلوک `@supports` بزرگ‌تر شده‌اند چون سوپرالیپس
نسبت به کمان دایره‌ای «تنگ‌تر» دیده می‌شود.

**۳. مقیاس تایپوگرافی** — از روی فریم فیگما درآمده و ستون چپ دقیقاً همان هندسه را
می‌دهد (کارت آمار ۲۶۳×۲۶۳، Level ۵۴۱×۳۰۰، Achievements ۵۴۱×۲۰۵، Challenge ۵۴۱×۲۲۰):

| | سایز |
| --- | --- |
| تیتر Hero | ۱۰۰ |
| عدد آمار / فیلد / Boost | ۵۸ / ۶۰ / ۵۶ |
| `Level 4` | ۶۲ |
| لیبل کارت | ۱۶ |
| ردیف‌های Info | ۱۷ |
| ارتفاع CTA | ۷۴ |
| radius کارت | ۶۰ (squircle) |

**۴. گرید مربعی** — کارت‌های آمار `aspect-ratio: 1 / 1` هستند و دو ستون با
`align-items: stretch` هم‌ارتفاع می‌شوند (CTA با `margin-top: auto` ته ستون می‌چسبد).

## نورپردازی، گرین و مقیاس سیال

**۱. لایت‌ریگ** — سطح‌ها رنگ خودشان را ندارند؛ همه از چند منبع نور روشن می‌شوند
(`.app__orb--*` در [base.css](src/styles/base.css)): یک key light بیرون از قاب سمت چپ
با یک هسته‌ی داغ که روی کارت اول می‌ریزد، یک fill سرد از پایین-راست و یک rim بالای تیتر.
منحنی Level هم خودش منبع نور است (`.level__bloom--a/b` پشت SVG). دکمه‌ی CTA و بج
پیش‌بینی دیگر fill تخت نیستند: شیشه‌ی تیره‌اند با نوری که از زیرشان نشت می‌کند
(`radial-gradient` در ۱۴۵٪ ارتفاع + `inset` box-shadow).

**۲. گرین** — یک تایل `feTurbulence` به‌صورت data-URI روی کل صفحه با
`mix-blend-mode: overlay` و opacity ‎۰٫۱۶‎، به‌علاوه‌ی یک شیفت آرام ۷ ثانیه‌ای.
بدون آن گرادینت‌های تیره banding می‌گیرند و «دیجیتال» دیده می‌شوند.
با `prefers-reduced-motion` انیمیشنش خاموش می‌شود.

**۳. پالت یخی** — هیو از ‎۲۲۴°‎ به ‎~۲۱۰°‎ آمده و اشباع حدود ۴۰٪ کم شده، پس نور
مثل نور سرد روز خوانده می‌شود نه آبی نئون.

**۴. یک صفحه، بدون اسکرول** — کل چیدمان روی یک فریم ۲۰۰۰×۱۵۰۰ «design px» بسته شده و
هر طول به `rem` سیال تبدیل شده:

```css
html { font-size: min(0.5vw, 0.653vh); }   /* 1rem = 10 design px */
```

ارتفاع ذاتی کامپوزیشن دقیقاً ‎150rem‎ است، پس ترم عمودی تضمین می‌کند محتوا هیچ‌وقت از
‎~۹۸vh‎ بیشتر نشود — روی نمایشگر پهن، پنل به‌جای بریده‌شدن فقط باریک‌تر می‌شود.
هرلاین‌های ۱px عمداً px مانده‌اند تا تیز بمانند.

> **تریدآف:** چون کارت‌های آمار مربع‌اند، عرضشان به ارتفاعشان قفل است. یعنی روی
> نمایشگر ۱۶:۹ برای اینکه همه‌چیز یک‌صفحه‌ای بماند پنل حدود ۵۲٪ عرض صفحه می‌شود
> (روی ۴:۳ و ۱۶:۱۰ پهن‌تر). زیر ۱۱۸۰px هم چیدمان تک‌ستونه و اسکرول‌دار می‌شود.

## ربات پشتیبانی (Onee)

آواتار پروسیجرال `@bible-strong/avatar-react` در گوشه‌ی پایین-راست صفحه، به‌عنوان
ربات پشتیبانی پنل. سه لایه دارد:

**۱. نگاه‌کردن به موس — داده‌محور، نه دستی.** هر اکسپرشن در فایل آواتار یک چرخش سر و
آفست چشم دارد؛ [gaze.js](src/avatar/gaze.js) از روی همان اعداد برای هر اکسپرشن یک
بردار نگاه می‌سازد و نزدیک‌ترین را به جهت مکان‌نما انتخاب می‌کند:

```
head.y → یاو   (+ راست، − چپ)
head.x → پیچ   (+ بالا، − پایین)
eyes.y → آفست چشم (۷ حالت استراحت، + پایین)
```

اکسپرشن‌های چشم‌بسته یا نامتقارن از استخر ردیابی حذف می‌شوند. چون همه‌چیز از خود JSON
درمی‌آید، اگر فایل آواتار را با کاراکتر دیگری عوض کنید باز هم کار می‌کند.

**۲. لایه‌ی presence.** بی‌حرکتی ۱۵ ثانیه → `bored`، ۲۸ ثانیه → `drowsy`،
۵۰ ثانیه → `sleeping`. اولین حرکت موس → `waking`.

**۳. واکنش‌ها.** هر ۲۳ انیمیشن یک تریگر واقعی در پنل دارد:

| انیمیشن | تریگر | | انیمیشن | تریگر |
| --- | --- | --- | --- | --- |
| `shy` | اولین لود | | `confused` | تایپ کاراکتر غیرعددی |
| `idle` | موس بیرون از پنجره | | `sad` | مخاطب صفر |
| `listening` | فوکوس روی فیلد | | `scared` | بیش از ۴۰هزار مخاطب |
| `searching` | تایپ عدد | | `angry` | رسیدن به سقف ۹۹۹٬۹۹۹ |
| `curious` | باز شدن دراپ‌داون | | `excited` | بوست ≥ ۴٫۲ |
| `surprised` | تغییر سگمنت | | `suspicious` | بوست ≤ ۱٫۶ |
| `happy` | هاور / تغییر ایجنت | | `playful` | دکمه‌ی وسط / دابل‌کلیک |
| `laughing` | کلیک روی آواتار | | `thinking` | باز کردن Info |
| `working` | حین ارسال (sticky) | | `celebrate` | موفقیت ارسال |
| `proud` | بعد از celebrate | | `bored`/`drowsy`/`sleeping`/`waking` | presence |

همه‌ی انیمیشن‌ها `loop` هستند، پس `onAnimationEnd` هرگز شلیک نمی‌شود؛ مدت هر واکنش از
جمع `holdMs + transitionMs` مراحلش حساب می‌شود. `working` تا `release()` سرجایش می‌ماند.

> **دو نکته درباره‌ی فایل آواتار:**
> ۱) `tipRoundness` و `baseRoundness` در فایل شما ‎2‎ هستند ولی
> `avatar-core@0.1.0` هر roundness را ۰ تا ۱ اعتبارسنجی می‌کند و کل تعریف را رد
> می‌کرد. فایل شما دست‌نخورده ماند و در [definition.js](src/avatar/definition.js)
> موقع لود clamp می‌شود (با لاگ در کنسول). اگر شکل نوکِ مخروط فرق داشت، از ادیتور با
> مقدار داخل رنج دوباره export کنید.
> ۲) این پکیج React 19 می‌خواهد، پس پروژه از React 18 به 19 ارتقا داده شد.

## ربات پشتیبانی گوشه‌ی صفحه

آواتار `Onee` (پکیج `@bible-strong/avatar-react`) گوشه‌ی پایین-راست می‌نشیند:
با چشم‌هایش مکان‌نما را دنبال می‌کند، روی هاور چشمک می‌زند، و با کلیک یک پنل
پشتیبانی باز می‌شود که خودش به بالای آن dock می‌شود و با TTS جواب می‌دهد.

### سه واقعیتِ رانتایم که کل طراحی را شکل داد

**۱. پلک‌زدن فقط داخل انیمیشن وجود دارد.** `blinkOpacityAt` در core مقدار
`animation.blink` را می‌خواند، پس آواتاری که با prop `expression` رانده شود
هیچ‌وقت پلک نمی‌زند. برای همین نگاه به‌صورت *انیمیشن* بیان شده نه اکسپرشن:
یک انیمیشن تک‌استپ به‌ازای هر سلول شبکه — پلک‌زدن مجانی می‌آید.

**۲. تغییر مستقیم اکسپرشن با ۴۲۰ms هاردکد tween می‌شود** (`durationMs: 420`).
داخل انیمیشن اما هر استپ `transitionMs` خودش را دارد، پس ردیابی روی ۱۵۰ms
تنظیم شده و خیلی سریع‌تر است.

**۳. سقف‌ها**: `expressions` حداکثر ۱۲۸، `animations` حداکثر ۶۴، حجم ۲۵۶KB.
رد شدن از هرکدام کل تعریف را باطل می‌کند و آواتار بی‌صدا ناپدید می‌شود.
الان: **۸۷/۱۲۸ اکسپرشن، ۵۹/۶۴ انیمیشن**.

### چرا مودهای آرتیست کنار گذاشته شدند

`happy` و `laughing` از `joyful-wide` استفاده می‌کنند که ارتفاع چشمش **۷۶** واحد
است در برابر **۴۰** نرمال — روی هاور مثل گشادشدن غیرطبیعی چشم دیده می‌شد. پس
`wink` و `talking` سنتز شدند: هر دو کلونِ `neutral` هستند، شکل چشم عوض نمی‌شود.

| رویداد | انیمیشن |
| --- | --- |
| حالت عادی | شبکه‌ی نگاه ۱۱×۵ + پلک |
| هاور | `wink` (سنتزی، `once`) |
| باز کردن چت | `wink` |
| نوشتن جواب | `thinking` |
| منتظر سؤال | `listening` |
| در حال حرف‌زدن | `talking` (سنتزی، `pingPong`) + حلقه‌های موج |

### چرخش نرم سر

سقف ۶۴ انیمیشن یعنی شبکه‌ی نگاه بیشتر از ~۵۵ سلول نمی‌شود، و روی بازه‌ی ۵۲ درجه
هر پله ۵٫۲ درجه می‌افتد — همان چرخش پله‌پله. پس چرخش سر از سیستم اکسپرشن جدا شد:

- **لایه‌ی گسسته** (شبکه) فقط جهت چشم داخل صورت را می‌دهد. بازه‌اش عمداً کوچک شد
  (`YAW` از ۲۶ به ۱۳، `PITCH` از ۱۵ به ۸) و بلندِ هر پله به ۲۶۰ms `smooth` رفت تا
  کوانتیزه‌شدن دیده نشود.
- **لایه‌ی پیوسته** (`.agent__tilt`) کلِ چرخش را می‌برد: `--gx` / `--gy` در هر فریم
  مستقیم روی CSS custom property نوشته می‌شوند — نه state ری‌اکت، وگرنه هر فریم
  یک رندر می‌شد — و `rotateY`/`rotateX` روی GPU کامپوز می‌شود.

**نگاشت زاویه‌ای:** نرمال‌سازیِ «هر سمت جدا» (تقسیم بر فضای موجود در همان سمت) روی
سمتی که آواتار به آن چسبیده فرو می‌ریخت؛ چون گوشه‌ی راست است، نگاه در ۶۰ پیکسل از
۰ به کامل می‌پرید. حالا یک شعاع مرجع واحد (`REACH` × بزرگ‌ترین بعد viewport) برای
هر دو جهت استفاده می‌شود: متقارن، پیوسته، و سمت تنگ فقط هیچ‌وقت به انحراف کامل
نمی‌رسد — که رفتار واقعیِ نگاه‌کردن به نقطه‌ای نزدیک هم همین است.

اندازه‌گیری‌شده: بیشترین پرش بین نمونه‌های متوالی **۰٫۱۱** روی محور افقی و **۰٫۱۶**
روی عمودی، یکنواخت و بدون پرش موقع عبور از مرکز.

### افکت حرف‌زدن

`SpeechSynthesisUtterance.onboundary` به‌ازای هر کلمه شلیک می‌شود؛ المان موج با
`key={beat}` دوباره mount می‌شود تا انیمیشنِ ripple **هم‌زمان با صدا** ری‌استارت
شود، نه اینکه آزاد بچرخد. اگر مرورگر TTS نداشته باشد یا صدا mute باشد، همان حالت
`talking` با یک تخمین زمانی از روی طول متن پخش می‌شود.

> نکته‌ی ظریفی که باگ داد: کال‌بک‌های چت اگر arrow اینلاین باشند در هر رندر هویت
> جدید می‌گیرند، و افکتِ خوش‌آمدگویی در `SupportChat` که به آن‌ها وابسته است دوباره
> اجرا شده و `talking` را با `listening` بازنویسی می‌کرد. الان با `useCallback`
> پایدارند و `listen` هم موقع حرف‌زدن کاری نمی‌کند.

تنظیم‌ها: `YAW`/`PITCH`/`TRACK_MS`/`BLINK` در [gaze.js](src/avatar/gaze.js)،
`SPAN` در [SupportAgent.jsx](src/components/SupportAgent.jsx). ژست فعلی روی
`data-mood` همان المنت هست تا دیباگ ساده باشد. جواب‌ها در
[answers.js](src/avatar/answers.js) قاعده‌محورند (نه LLM) و از وضعیت زنده‌ی پنل
تغذیه می‌شوند.

## TTS سمت سرور (برای VPS)

صدای پیش‌فرض مرورگر روی ویندوز فقط SAPI5 قدیمی است (David/Mark/Zira) و صداهای
«Natural» ویندوز ۱۱ اصلاً به مرورگر داده نمی‌شوند. برای همین موتور به سمت سرور
منتقل شد.

```
POST /api/tts        { "text": "..." }   →  audio/wav
GET  /api/tts/health                     →  { ready, engine, model, voice, ... }
```

### دو موتور — و عددهای اندازه‌گیری‌شده

`TTS_ENGINE` تعیین می‌کند کدام آداپتور لود شود؛ هر دو دقیقاً سه تابع
`init/status/synthesise` را می‌دهند. **هر دو را روی همین ماشین اجرا و اندازه‌گیری
کردم** (i5-13420H، ۱۲ ترد، CPU خالص):

| جمله | Kokoro (q8) | Piper (ryan/high) |
| --- | --- | --- |
| «Your boost is three point six.» | ۲۸٫۰۹s | ۲٫۳۹s |
| «You are sending to twenty five thousand contacts.» | ۲۹٫۴۸s | ۲٫۳۱s |
| «Predicted deliverability is…» | ۳۰٫۴۹s | ۲٫۶۱s |
| از کش | ۰٫۰۳s | ۰٫۰۷s |

**Kokoro روی CPU حدود ۷ برابر realtime است — برای چت زنده جواب نمی‌دهد.** بررسی
کردم که گلوگاه کجاست: phonemizer فقط ۰٫۱۱ ثانیه می‌گیرد، یعنی تقریباً تمام آن ۲۹
ثانیه اینفرنس مدل است. تعداد ترد را هم دستی به ۸ بردم (`kokoro-js` گزینه‌ی
`session_options` را فوروارد نمی‌کند، پس مدل مستقیم از
`StyleTextToSpeech2Model` ساخته می‌شود) — تفاوتی نکرد؛ onnxruntime روی این مدل
حدود ۱٫۵ هسته از ۱۲ را مشغول می‌کند.

پس **پیش‌فرض روی Piper است.** Kokoro کیفیت بهتری دارد و کد و آداپتورش سرِ جا مانده؛
اگر VPS قدرتمند یا GPU داشتی، `TTS_ENGINE=kokoro` کافی است.

صدای فعلی **`en_US-ryan-high`** است — همان `ryan/high` که انتخاب کردی. نکته‌ای که
باید بدانی: `ryan/high` یک صدای **Piper** است و در Kokoro وجود ندارد؛ Kokoro
مجموعه‌ی صدای خودش را دارد (`am_*` مرد آمریکایی، `af_*` زن آمریکایی،
`bm_*`/`bf_*` بریتانیایی) و روی `am_michael` تنظیم شده. لیست کامل در پاسخ
`/api/tts/health` می‌آید.

### ورکرهای ماندگار

Piper برای هر پروسه ~۱٫۸ ثانیه صرف لود مدل ۱۲۰MB می‌کند، پس یک پروسه به‌ازای هر
درخواست یعنی هر جمله این هزینه را دوباره می‌دهد. آداپتور از حالت `--json-input`
استفاده می‌کند: پروسه زنده می‌ماند، مدل یک بار لود می‌شود و هر جمله یک خط JSON روی
stdin است؛ piper هم مسیر خروجی را روی stdout چاپ می‌کند که سیگنال اتمام است.

> روی همین ویندوز، حالت ماندگار **کندتر** درآمد (~۳٫۲s در برابر ~۲٫۴s) چون هر
> رندر یک فایل موقت می‌نویسد و می‌خواند و Defender تازه‌نوشته‌ها را اسکن می‌کند.
> روی VPS لینوکسی این هزینه وجود ندارد و حذف لود دوباره‌ی مدل برنده است — که
> هدف این پروژه است.

### اجرا

```bash
npm run tts     # سرویس TTS روی 127.0.0.1:8787
npm run dev     # ویت، با proxy روی /api
```

بار اول وزن‌های مدل از HuggingFace دانلود و روی دیسک کش می‌شوند، پس اولین
`npm run tts` کند است. بعد از آن آفلاین کار می‌کند.

### استقرار روی VPS (اوبونتو)

```bash
npm ci && npm run build          # خروجی در dist/
cp .env.example .env             # و مقادیر را تنظیم کن
node server/tts.mjs              # با systemd نگهش دار
```

nginx فقط `/api` را پروکسی می‌کند:

```nginx
location /api/ { proxy_pass http://127.0.0.1:8787; }
location /     { root /var/www/panel; try_files $uri /index.html; }
```

### چیزهایی که در سرویس رعایت شده

- **کش دیسکی** بر اساس هش متن. جواب‌ها تکراری‌اند (چند جمله با چند عدد متفاوت)،
  پس بیشتر درخواست‌ها به یک خواندن فایل تبدیل می‌شوند (`X-TTS-Cache: hit`) —
  که با Kokoro مهم است، چون تولید هر جمله چند ثانیه CPU می‌برد.
- **بدون shell**: در آداپتور Piper متن از stdin می‌رود و آرگومان‌ها آرایه‌اند، پس
  چیزی که کاربر تایپ می‌کند نمی‌تواند به آرگومان یا توکن شل تبدیل شود.
- سقف ۶۰۰ کاراکتر، محدودیت نرخ per-IP، و صف با سقف همزمانی (تولید CPU-bound است؛
  بدون صف چند درخواست هم‌زمان سرور را می‌خواباند).
- **degrade تمیز**: اگر موتور بالا نیاید سرویس ۵۰۳ برمی‌گرداند و کلاینت خودکار به
  `speechSynthesis` مرورگر برمی‌گردد. سایت بدون سرویس هم کار می‌کند.

### افکت حرف‌زدن حالا از خود صدا می‌آید

با صدای سروری دیگر `onboundary` نداریم، که در عمل بهتر شد: یک `AnalyserNode`
روی مسیر صدا نشسته و RMS واقعی موج را هر فریم می‌دهد. آن مقدار مستقیم روی
`--level` نوشته می‌شود و حلقه‌ها و مقیاس آواتار از همان می‌آیند — یعنی آواتار به
**خود موج صدا** واکنش نشان می‌دهد نه به یک ریتم حدسی. در حالت fallback مرورگری،
`--level` از مرز کلمات ساخته می‌شود.

## نکته‌ها

- همه‌ی رنگ‌ها از CSS variable در `src/styles/tokens.css` می‌آیند — تم را از همان‌جا عوض کنید.
- فونت‌ها: Outfit (نمایشی) + Inter (متن) از Google Fonts در `index.html`.
- محاسبات پیش‌بینی (open rate، deliverability، leads) در `src/data.js` است؛ برای اتصال به
  بک‌اند فقط همان توابع را با پاسخ API جایگزین کنید.
- ریسپانسیو: زیر ۱۰۸۰px گرید تک‌ستونه و زیر ۶۲۰px کارت‌های آمار زیر هم می‌روند.
